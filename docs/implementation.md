# 設計との対応・実装判断

## 元資料

添付された「マルチテナントSaaS化 詳細設計書 Ver.1.0」を基準としています。参照先の要件定義書 Ver.1.1、旧コード、モックアップは提供されていません。着手時のmainはREADMEのみでした。

## データと権限

- `tenants/{id}` 配下に予約・顧客・スタッフ・招待を保存。
- UIDをスタッフのドキュメントIDとする。ルールはCustom Claimsに加えて現存するスタッフ文書を検証。
- 設計案から強化し、スタッフ・招待・人数のクライアント書き込みは拒否。信頼されたFunctions／初期化スクリプトからのみ更新。
- 招待の平文トークンを保存せず、SHA-256のハッシュをドキュメントIDとする。平文は発行時のみ返す。URLのfragmentに入れる。
- `memberships/{uid}` はサーバー専用。複数店舗の同時招待で同じユーザーが二重所属しないようトランザクションで確定。
- 設計書の単一 `tenantId` Claimに合わせ、1アカウント1店舗とする。複数所属と店舗切替は、所属・認可モデルの別設計が必要なため未実装。
- 店舗作成は信頼されたbootstrapのみ。一般ユーザーの自己発行は不可。
- Adminが他のAdminを招待できる。スタッフの削除・権限編集は詳細設計のタスク範囲にないためUIなし。
- 予約状態変更はドラッグではなく選択式。カンバンも現在のカレンダー期間の予約を表示し、範囲を明示。
- 顧客は予約作成時に作成。顧客検索・重複統合・独立した顧客管理画面は未実装。予約編集時の顧客名は予約上の表示名を変更。
- 招待の発行上限は要件数値がないため未設定。staffCountは参加時に原子的に増加。

## 招待の一貫性

Firestoreトランザクションで招待消費・スタッフ作成・人数更新・所属確定。その後Custom Claimsを更新する。Claims更新に失敗した場合、同じユーザーが同じ招待を再受諾することで回復できる。別ユーザーの再利用は拒否。メール認証が必要。

## 検証

- 単体: 月末／閏年／年跨ぎ、招待期限境界・失効・再利用・識別子。
- Firestoreエミュレーター: 未認証、他店舗、権限変更、管理者Claimと実データの不一致、予約入力検証。
- Auth + Functions + Firestoreエミュレーター（テスト実装済み、ローカルはUnixソケットEPERMにより実行未完了。CIで実行）: 非管理者発行拒否、同時受諾、再試行、人数、失効。
- CI: 上記とビルド。Node22 / Java21。
- ブラウザー: 検証ツールのデーモンが環境内で起動に失敗。目視・操作の検証は未完了。
- 本番Firebaseへのデプロイ、本番データ移行、顧客へのβ導入は未実施。

## 次の導入ゲート

1. 本番または検証用FirebaseプロジェクトとWeb設定を確定。
2. 初期管理者作成、認証と招待のブラウザー操作確認。
3. 要件定義書・モックアップ・既存データがあれば差分確認。移行スキーマのマッピング、バックアップ、移行件数検証。
4. 管理者／スタッフ／異なる店舗のアカウントで受入確認。
5. Hosting / Rules / Functionsを対象プロジェクトへデプロイしβ店舗で確認。

移行スクリプトは元データが不明なためテンプレート段階。実データに対する移行完了を意味しません。
